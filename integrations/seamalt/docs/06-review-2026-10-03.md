**注意（今回見つかった実害）**: RLS で拒否された SELECT はエラーにならず「0件」になる。直接出荷（index.html `recordDirectShipment`）は顧客の価格ランクと備考（仲卸の判定）を customers から読むが、スタッフキーの無い端末では空が返り、エラーも出ずに「スタンダード・仲卸なし」として登録される。9月のノブレスオブリージュ経由の出荷11件の備考（memo）が空だったのはこれが原因の可能性が高い（同じ顧客でも8/31は入り9/4は空）。
→ 是正: 直接出荷の顧客情報は `staff_lookup_customer_id` と同じくキー不要の関数（価格ランクと仲卸タグだけ返す）で取り、取れなかったら画面にエラーを出す。段階Bでも同じ「無言の0件」が起きるため、キー必須にする表を読む画面には「0件かつキー無し」を検知して知らせる表示を先に入れる。

## 2. aud を MCP の URL にする（Custom Access Token Hook）
- 公式ドキュメント（Supabase OAuth Server「Token Security」）に、フックで OAuth クライアントごとに aud を変える例がある。フックは OAuth を含む全トークン発行で呼ばれ、`client_id` を受け取る。**`resource` パラメータは渡らない**。
- 案: `sql/30_access_token_hook_aud.sql`。許可リスト（client_id → aud）に載ったクライアントだけ aud を差し替え、通常のログインや他のクライアントは変えない。MCP 側は aud=MCP の URL だけを受け入れる（`authenticated` を外す）。
- ローカルで確認済み: 許可リストのクライアントだけ差し替え・他のクラームは保持・取り消したクライアントは変えない・anon/authenticated/seamalt_mcp は実行不可・MCP は aud=authenticated を 401、差し替え後を通す（結合試験の14章）。
- 未確認: (1) ChatGPT の DCR で client_id が決まるのは接続時なので、「接続 → client_id 確認 → 許可リストに追加 → 再接続」の手順になる。(2) aud を変えたトークンを PostgREST が受け付けるか。受け付けなければ、シーモルト用トークンでは REST を直接叩けない（望ましい）。(3) フックが例外を出すと全員のトークン発行が止まる。本番の Supabase Auth 利用者は本人1名だけで、業務画面は Supabase Auth を使っていないため、影響は本人のログインと OAuth に限られる。

## 3. 出荷の負担を抑えた認証（提案）
| 方式 | 出荷担当の手間 | 失くした端末の止め方 | 評価 |
|---|---|---|---|
| 今のスタッフキー（共有リンク `#skey=` で端末に1回設定） | 端末ごとに最初の1回だけ（リンクを開く） | キーを変える＝**全端末で再設定** | 仕組みは既にある。紛失時の手間が大きい |
| **端末登録（推奨）**: 管理者が端末ごとの登録リンク／QR を発行 → 開くと端末用の鍵が保存される。ヘッダは今と同じ形で送る | 端末ごとに最初の1回（QR を読むだけ）。毎日の入力なし | 管理画面でその端末だけ無効化 | 既存の `staff_key_header_ok()` を「端末鍵の照合も可」に広げるだけで、画面側の変更は小さい |
| 職員ごとのログイン（Supabase Auth） | 職員ごとにメール・パスワード | アカウント停止 | 出荷・打刻の現場には重い |

端末登録の要点: 鍵はサーバー側にハッシュだけ保存・端末名と最終利用日時を記録・有効期限（例: 180日）と失効・登録リンクは1回限りで短命（10分）。出荷用の共有端末（1〜2台）を先に登録すれば、段階Bを入れても現場の操作は変わらない。

## 4. 内部資料の公開状況（実測）
- **GitHub リポジトリ `okillcalco-bot/tateyama-gibier` は公開（public）**。そのため、リポジトリ内のすべて（CLAUDE.md・AI_HANDOFF.md・migrations 120本・docs・alco-os の設計書・tests・staff-docs の就業規則/賃金規程など）は誰でも読める。

- 秘密値そのもの（service_role キー・パスワード・トークン）はリポジトリに見つからなかった（変数名の記述のみ）。ただし CLAUDE.md や migrations には「anon キーで注文が読める」等、上記の弱点の説明があり、公開キーと合わせると悪用の手順になる。
- staff-docs は manual-app.html から職員向けにリンクされている規程類（健康診断の案内を含む。個人の結果ではない）。

# 精肉・在庫管理・受注・出荷のつくり（要求仕様づくりのための現状説明）

作成: 2026-11-27　対象: 館山ジビエセンター基幹システム（本番稼働中）
宛先: 捕獲・受入・解体の要求仕様をまとめるシステムエンジニア
数字は 2026-11-27 時点の本番の実測。全体の設計書は `docs/system-design.md`。

---

## 0. まず押さえてほしいこと

1. **軸は「1頭の一生が1本の線でつながること」。**
   生態（捕獲）→ 個体 → 精肉 → 加工 → 販売 → 食べた人の声。どの画面・表もこの線を切らないことを判断基準にしている。
   捕獲・受入・解体の仕様は、この線の**起点（個体番号）**をつくる部分になる。
2. **線をつなぐ鍵は個体番号 `label_id`（例 `TGC-08-T429`）。** 精肉以降はすべてこの番号で個体にさかのぼる。
   番号の形・採番方式・バーコード・ラベルは**既存を変えない**前提で設計してほしい（現場のラベル・在庫・請求がすでにこれで動いている）。
3. **元データは追記のみ。** 個体・在庫・注文は書き換えず、訂正は指示と備考を残して行う。

```
捕獲・受入・解体（今回の仕様範囲）
   individuals.label_id（TGC-08-T429）・体重・性別・捕獲地・止めさし・ランク・放射能検査
        │
        ▼ 精肉
   inventory（部位パック 1パック=1行）ident_code / scan_code（8桁バーコード）
        │                 └─▶ 加工（ミンチ・スライス）: 原料パック→加工品パック（processing_log）
        ▼ 受注・出荷
   order_items.inventory_id ─ orders ─ shipments（送料・送り状）─ documents（納品書・請求書）
        │
        ▼
   ラベルのQR → s.html（この肉の物語）→ meal_voices（食べた人の声）
```

## 1. 精肉（個体 → 部位パック）

### 1.1 画面と操作
- 画面: `index.html` の「精肉入力」タブ（タブレット・PC）。
- 流れ: 個体を選ぶ → 部位を選ぶ → 計量（袋の重さ 10g を引く）→ 登録 → ラベル印刷。1パックごとに繰り返す。
- 前日の続きから再開しても、ラベルと在庫の番号がずれないようにしてある（2026-11-09 修正）。

### 1.2 1パック = `inventory` の1行（tier=2）
| 列 | 中身 | 例 |
|---|---|---|
| `individual_id` | 個体番号（線の鍵） | `TGC-08-T458` |
| `ident_code` | パックの識別コード `{個体}-{部位略号}-{連番}` | `TGC-08-T458-BA-5` |
| `scan_code` | 8桁バーコード。DB関数 `tgc_reserve_scan_codes` で払い出す | `10008096` |
| `barcode_num` | 部位略号 | `BA` |
| `part_name` | 部位名（小売パックは ` [小売]` 付き） | `バラ` |
| `weight_kg` | 正味重量 | `1.000` |
| `grade` | ランク（並・上・極上）。個体のランクをパックに写す | `並` |
| `lot_code` | `{個体}-{部位}-{日付}-{連番}` | `T458-BA-20261125-005` |
| `status` | 状態（1.4） | `在庫` |
| `processed_at` / `processed_by` / `operator` | いつ・誰が | |

### 1.3 部位略号（実データで使われているもの）
ロース `RO`・ヒレ `HI`・肩ロース `KR`・カタ `KT`・バラ `BA`・モモ `MO`（ソト `MOS`／ウチ `MOU`／シンタマ `MOT`）・スネ `SN`・ネック `NK`・チチカブ `CB`・
ミンチ用 `MU`・スライス用 `SL`・味肉用 `AJ`・唐揚げ用 `KG`・ペットフード用（骨あり `PF1`／なし `PF2`）・
内臓（レバー `LV`・ハツ `HT`・フワ `FW`・タン `TN`・ショウチョウ `SC`）・骨・
**枝肉のまま出すもの** `ED`（全体）・`EDU/EDN/EDS`（上・中・下）。

> 解体の仕様との接点: 枝肉で出す個体は、精肉せず `ED` のパックを1〜数行作って出荷する（加工施設あて）。
> 解体の段階で「枝肉で出すか・精肉するか」を決めるなら、その判断をどこに記録するかを決めてほしい。

### 1.4 ラベル
- 印字: 産地・獣種／個体管理番号／部位／正味重量（袋の重さを引いた値）／消費期限（冷凍で約1年）／保存温度／バーコード（`scan_code`）／`ident_code`／QR（`s.html?c=<scan_code>` この肉の物語）／施設名・住所。
- バーコードは桁数を実測して決めた（読み取り限界のため、`ident_code` ではなく8桁の `scan_code` を印字）。

### 1.5 実測（説明用の数字）
精肉まで終えたイノシシ201頭: 食べるお肉は**体重の約23%（1頭 約9.2kg）**、ほかにペットフード用 約2.8kg。
内訳は 希少部位（ロース・ヒレ）11%／ブロック 42%／加工向け 47%。業務アプリの「1頭から取れる量」タブで最新値を出せる（PR #440）。

## 2. 加工（部位パック → 加工品パック）

- 画面: `index.html` の「加工処理」タブ。
- 流れ: 原料パックをスキャン（複数個体を混ぜてよい）→ 加工の種類（ミンチ・スライス 1.5/2/3/4.5/5mm など）→ できあがりのパックを登録・ラベル印刷。
- データ:
  - まとめ番号（バッチ）: `TGC-SLB-YYYYMMDD-nnn`（スライス）・`TGC-MIB-…`（ミンチ）
  - できあがりパック: `inventory` tier=3、`ident_code` は `TGC-SL-YYYYMMDD-nnn`／`TGC-MI-…`、`parent_inventory_id` に原料の1つ
  - `processing_log`: 原料パック → バッチ（`weight` に原料の重さ）、バッチ → できあがり（`result_weight_kg`）を1行ずつ。これで加工品から個体にさかのぼれる
  - 原料パックは `status=加工済` になる
- ラベルの「原料」欄に、混ぜた個体番号を最大4つ＋「他」で印字。
- 取消のときも加工記録は消さない（2026-11-07 修正）。

## 3. 在庫管理

### 3.1 状態（`inventory.status`）
| 状態 | 意味 | 件数（部位パック／加工品） |
|---|---|---|
| `在庫` | 冷凍庫にある | 891 ／ 553 |
| `引当済` | 注文に割り当てた（出荷前） | 13 ／ 3 |
| `出荷済` | 出荷した | 4,071 ／ 124 |
| `加工済` | 加工の原料に使った | 308 ／ 1 |
| `廃棄` | 廃棄 | — |
| （削除） | `deleted_at` を入れる。行は消さない | |

遷移: 精肉で `在庫` → 注文に割当で `引当済` → 出荷で `出荷済`。加工に使うと `加工済`。

### 3.2 画面
- `index.html` の「在庫一覧」タブ: 部位・ランク・状態・個体で絞り込み、件数と重量。1,000行を超えても全件を数える。
- 加工品の棚（ジャーキー・味付け肉など個体に紐づかない商品）は `products` と `product_movements` で数で管理する（通販・道の駅の出荷で引く）。

### 3.3 注意（実データの事情）
- 4〜7月の手書きラベル時代の在庫は、いったん一括で `出荷済` にした（注文に紐づかない出荷済 2,249件）。実物が冷凍庫に残っていることがある。
  → 出荷で「出荷済なのに注文に紐づかないパック」が出たら、使う前に確認する決まり。
- 在庫の置き場所（`location_code`）はほぼ未入力。

## 4. 受注

### 4.1 入口（注文の入り方）
| 入口 | 番号 | 件数 | 流れ |
|---|---|---|---|
| 電話・LINE・手書き（**主流**） | `DIR-YYYYMMDD-HHMMSS` | 380 | 出荷タブで「直販（注文なし）」として、出荷と同時に注文を作る |
| 取引先の注文ページ `order.html` | `ORD-…` | 18 | 取引先が部位と kg で注文 → 出荷タブで在庫を割当 |
| BASE（ネットショップ） | `BASE-…` | 19 | BASE API から取得 → 出荷 |
| 通販（さとふる・まいぷれ・AWAWA） | `marketplace_orders` | — | メール → 取込 → 出荷で加工品の棚を引く |
| 仲卸経由（ノブレスオブリージュ・トレタテ） | 上と同じ | — | お店名義で注文、請求は仲卸あてにまとめる（仲卸用の注文画面は PR #436・未適用） |

### 4.2 データ
- `orders`: 注文番号・顧客・注文日・納品希望日・時間帯・届け先・合計・状態（実データは `発送済` 410／`キャンセル` 8）・備考。
- `order_items`: 1明細 = 1パック（`inventory_id`）。単価・金額・**単価の根拠 `price_source`**・適用ランク・パックの選び方 `pick_method`（`scan`=バーコードで読んだ／`typed`／`picker`・`dropdown`=ラベルを読んでいない＝要現物確認）。
  注文ページの注文は `requested_kg`（希望重量）で入り、割当時に実重量で金額が決まる。
- 単価: `price_master`（獣種×部位×ランク〈並・上・極上〉×顧客区分〈スタンダード・ローカル・スタートメンバー・プレミアム・卸〉）＋顧客別単価。税込。
  単価表にない物（スライス・小売パック・アライグマなど）は都度決め、根拠を `price_source` に書く。
- 顧客: `customers`（866件）。顧客区分・住所・注文ページのログイン（お客様番号＋パスワード）。

## 5. 出荷

### 5.1 画面と操作
- 画面: `index.html` の「出荷処理」タブ。出荷待ちの注文の件数を一番上に出す。
- 流れ: 注文を選ぶ（または直販）→ パックのバーコードをスキャンして明細に割当 → 運送会社・サイズ・クール・送料・送り状番号 → 出荷確定 → 在庫が `出荷済`。
- 送り状は `index.html` から作れる（ヤマト・佐川）。

### 5.2 データ（`shipments`・388件）
| 列 | 中身 |
|---|---|
| `order_id` / `customer_id` | 注文・顧客 |
| `shipment_date` / `delivery_date` | 出荷日・お届け指定日 |
| `carrier` / `size_code` / `is_cool` | 運送会社・サイズ（60/80/100…）・クール |
| `freight` | 送料（税抜。請求書で10%を足す） |
| `package_count` | 個口 |
| `notes` | 送り状番号・箱ごとの内訳 |

- 送料表: `shipping_rates`・`shipping_areas`（例 ヤマト冷凍 関東: 60=800円・80=1,020円・100=1,300円）。

### 5.3 書類
- `order-admin.html`（受発注管理）で納品書・請求書・領収書（`documents`）。
- 決まり: 発行済みは黙って上書きしない／作っただけで送付済みとみなさない／訂正しても自動で再送しない／税・端数・締めは勝手に変えない。

### 5.4 放射能検査との関係
- 館山市・南房総市の個体は全頭検査が必須。**結果の判明日より前の出荷は確認対象**（加工施設あての枝肉は除く）。
- 出荷時に個体の `radiation_result_date` を見る。

## 6. 捕獲・受入・解体の仕様に入れてほしいこと（接続の条件）

| # | 精肉以降が前提にしていること | 現状 |
|---|---|---|
| 1 | 個体番号 `label_id` の形 `TGC-{年度2桁}-{地区記号}{3桁}`（T=館山市・M=南房総市・シ=シカ・ア=アライグマ） | 地区・種ごとの最大＋1で採番。**変えない** |
| 2 | 年度通し番号（イノシシ） | 前回の最大＋1 |
| 3 | 搬入時の体重 `weight_total` | 歩留まり・買取額・説明用の数字の元。947頭中945頭で入っている。必須にしてほしい |
| 4 | 獣種・性別・捕獲地区・捕獲方法・止めさし方法・捕獲者 | 947頭すべてで入っている |
| 5 | 緯度経度・推定年齢・体長・餌 | 列はあるがほぼ空（947頭中: 緯度経度 8・推定年齢 8・体長 78）。生態データとして取りたい |
| 6 | 肉のランク（並・上・極上）を個体に付ける時点と基準 | 個体単位で付けてパックに写す（947頭中530頭に入っている）。基準は数値化していない（脂の厚み mm を測る案あり） |
| 7 | 放射能検査の検査日・判明日・結果 | 手書きの速報から毎日反映（947頭中741頭に判明日）。出荷可否に使う |
| 8 | 枝肉で出すか精肉するかの判断 | 記録する場所がない（ED パックの有無で後から分かるだけ） |
| 9 | 原本の扱い | 今は Google スプレッドシートの「搬入・処理管理台帳」が原本で、DB に反映している。システムを原本にするかは未決 |
| 10 | 写真 | 捕獲時の看板写真（`image_url`）。DB の日次バックアップに入らない |

### 現状の弱いところ（仕様で解消したいもの）
- 個体番号は市に出す番号を兼ねており、繰り上げ・付け替えが起きると、ラベル・在庫・注文を手でたどる必要がある（変わらない内部番号を別に持つ案: `docs/proposals-2026-11-24.md` C-1）。
- 画面のコードに `TGC-08`（施設コード＋年度）が約90か所決め打ちで入っている（年度替わり・他施設展開で書き換えが必要）。
- 精肉・加工・出荷・請求の保存が1回の取引になっていない（途中失敗で一部だけ残ることがある）。一体保存の設計を進めている。
- 権限: ブラウザに埋め込んだ公開キーで多くの表を読み書きできる。段階的に閉じている途中（PR #435 ほか）。

## 7. 技術の前提（参考）
- 静的 HTML + Supabase（PostgreSQL・REST）直結。ホスティングは Vercel。PWA（`sw.js`・`manifest.json`）で現場の端末に入っている。
- DB の変更は `/migrations` に追加のみの SQL。既存の画面を突然止める変更はしない。
- 新しい業務OS（ALCO OS・Next.js）が同じ DB を使っている。表の変更は両方への影響を確認する。

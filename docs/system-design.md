版: 2026-11-23（現行の実装と本番DBを実測して作成）。変更したらこの文書も更新する。
対象: リポジトリ直下の業務アプリ群（静的HTML＋Supabase）。ALCO OS（`alco-os/`）・プロフィール（`profile/`）は対象外。

## 1. 目的と判断基準

**軸: 1個体の一生が1本の線で繋がっていること**（2026-08-26 合意）

```
生態（捕獲地・方法） → 個体（受入・検査） → 精肉（部位パック） → 加工 → 販売（注文・出荷・請求） → 食べた人の声
```

迷ったら「この変更は線を通すか」で決める。あわせて次を守る。

1. 品質上の欠陥（重なり・読めない・はみ出し）は判断を仰がずに直す
2. 勘で直さず、まず全件を数える
3. 同じ症状が3回出たら構造を変える
4. サイレント失敗を作らない（書き込みの失敗は必ず画面に出す）
5. 直したら、測り方を `tests/e2e/` に残す

### 1.1 線の太さ（実測）

| 段階 | 件数 | 前の段階からの割合 |
|---|---|---|
| 個体（削除除く） | 916頭（うち令和8年度 890） | — |
| 精肉まで（在庫パックがある個体） | 760頭 | 83% |
| 販売まで（注文に載ったパックがある個体） | 356頭 | 47% |
| 食べた人の声 | 39件 | — |

2026-08-26 時点（600頭→精肉235→販売49）から大きく太くなった。**精肉→販売の断絶が今も最大の課題**（在庫1,419パック）。

## 2. 全体構成

```
[現場の端末（スマホ・タブレット・PC）]
   │  PWA（sw.js / manifest.json）・静的HTML
   ▼
[Vercel] tateyama-gibier.vercel.app  ← GitHub main を squash merge で自動反映（約6分）
   │  ブラウザから直接
   ▼
[Supabase（PostgreSQL・Storage）] project: clpdyrehdgzgiidbfucj
   │  REST（PostgREST）・RPC（DB関数）・RLS
   ├─ Google Apps Script（通販メール取込: さとふる・まいぷれ・AWAWA）
   ├─ BASE（ネットショップ連携: base-callback.html / base_tokens）
   ├─ シーモルト（integrations/seamalt: 注文取込サーバー）
   └─ LINE（line_* 表: 受信・送信・グループ）
[Google Drive]  台帳スプレッドシート（捕獲データ原本）・領収書・実包管理簿など
```

### 2.1 技術の決まり

| 項目 | 決まり |
|---|---|
| 画面 | 1画面＝1つの静的HTML（ビルドなし）。共通JSは `admin-gate.js`・`finance-core.js`・`recon-core.js`・`recipes.js` |
| PWA | `sw.js`・`manifest.json`・ルートのファイル構成は**変えない**（現場のアプリが壊れる） |
| DB変更 | `migrations/` に**追加のみ**のSQL（119本）。トップレベルの DROP は書かない |
| 元データ | `individuals`・`inventory`・`orders` は書き換えない。訂正は本人の指示で行い、備考に記録 |
| テスト | `tests/e2e/`（198本）。Playwright＋架空データ。変更したら関連テストを全部流す |
| リポジトリ | **公開**。実データ・個人情報・秘密値を置かない |

## 4. 業務の流れ（線に沿って）

### 4.1 捕獲・受入（生態 → 個体）

1. 捕獲者が搬入 → `capture-form.html` で捕獲票を入力（捕獲日時・場所・方法・止めさし・体重・受入時刻・記録者）
2. 通し番号（年度通し）と個体番号（`TGC-08-T◯◯◯`＝館山市／`M◯◯◯`＝南房総市／`シ`＝シカ／`ア`＝アライグマ）を採番
3. 看板写真を撮影（`image_url`）
4. 原本は Google スプレッドシート「イノシシの搬入・処理管理台帳」（年度ごと）。DB へは `label_id` をキーに `individuals` へ反映
- 表: `individuals`（916）・`individuals_history`（変更履歴 2,423）・`hunters`（245）・`area_master`（190）

### 4.2 放射能検査（個体）

- 館山市・南房総市は**全頭検査が必須**（千葉県の解除対象外）
- 手書きの「検査結果速報」写真から、`individuals.radiation_test_date / radiation_result_date / radiation_result` に反映（ほぼ毎日・検査日＝判明日）
- 判明日より前の出荷は確認対象（加工施設あて枝肉は除く）
- 画面: `index.html` 放射能検査タブ・`capture-report.html`（台帳）

### 4.3 精肉（個体 → 部位パック）

1. `index.html` 精肉入力で部位・重さを入れてラベル印刷
2. 1パック＝`inventory` 1行（`ident_code`＝`TGC-08-T429-RO-3` 形式、`scan_code`＝8桁バーコード）
3. ランク（並・上・極上）は個体単位で付け、パックへ反映
- 表: `inventory`（5,645・在庫 1,419）・`processing_log`（3,785）

### 4.4 加工（パック → 加工品）

- ミンチ・味付け肉・ジャーキー等。原料パックを使用済みにし、加工品の棚数（`products` 30品）を増やす
- 表: `processing_log`・`products`・`product_movements`（912）

### 4.5 販売（注文 → 出荷 → 請求）

| 入口 | 流れ |
|---|---|
| 注文ページ（`order.html`） | 取引先が注文 → `orders` 受注 → 出荷タブで在庫を割当（スキャン）→ 出荷確定 |
| 電話・LINE・手書き（主流） | 出荷タブで「直販（注文なし）」として直接出荷 |
| 仲卸経由（ノブレスオブリージュ51店・トレタテ16店） | お店名義の注文＋備考／顧客備考の仲卸名 → 請求は仲卸あてにまとめる |
| 通販（さとふる・まいぷれ・AWAWA） | Gmail → Apps Script → `marketplace_orders` → 出荷で加工品の棚を引く |
| BASE | BASE API から取得 → 出荷 |
| イベント出店 | `sale_events`・`sale_event_items` |

- 出荷: `shipments`（375・送料あり 318）。送料表 `shipping_rates`・`shipping_areas`
- 単価: `price_master`（ランク別: 標準・地元・スタートメンバー等）＋顧客別単価 `customer_prices`
- 書類: `order-admin.html` で納品書・請求書・領収書（`documents` 209・`document_items`・`document_orders`）。発行済みは上書きしない・送付済みと見なさない・自動再送しない

### 4.6 食べた人の声（販売 → 声）

- ラベルの QR → `s.html`（この肉の物語：捕獲地・捕獲者・検査・部位）→ 感想を送る → `meal_voices`（39）

### 4.7 その周り（線を支える業務）

| 領域 | 画面・表 |
|---|---|
| 衛生（HACCP） | 清掃記録 `cleaning_logs`（3,009）・施設点検 `facility_check_logs`（4,581）・防虫 `pest_control_logs` |
| 産廃 | `sanpai.html`・`waste_weighings`・`waste_checklists` |
| 勤怠・給与 | `punch.html`・`attendance`（956）・`shifts`・`payroll.html`・`payroll_lines` |
| 会計 | `finance.html`・`bank_transactions`・`card_transactions`・`receipts`（領収書・部門 gibier/alco） |
| 買取 | `buyback.html`（捕獲者への買取金額通知・半期） |
| 解析 | 売上・捕獲条件・フードマイレージ・公的データ・LCA・収支 |

## 7. 権限とセキュリティ

### 7.1 方式

| 層 | 内容 |
|---|---|
| 公開キー（anon） | ブラウザに埋め込み。多くの表を読み書きできる（下記の課題） |
| スタッフキー | 管理操作は DB関数 `staff_key_ok()` で照合してから実行 |
| 注文ページ | 取引先はトークン（`portal_sessions`）経由の DB関数だけ。表を直接は読めない |
| 秘密値 | `app_secrets`・`base_tokens` は RLS で直接読めない。ブラウザ・会話・リポジトリに出さない |

### 7.2 課題（実測）

- **公開キーで行を削除できる表が 149**。注文・出荷・在庫・価格の表も読み書きできる
- 第1段（PR #435・未適用）: 注文・出荷・在庫・商品・価格の削除権限を外す／履歴に社内メモを送らない
- 第2段（未着手）: 現場画面を DB関数経由に移してから、読む・書くを閉じる。**既存画面を突然止めない**順で進める

### 7.3 承認が必要な操作

本番マイグレーション／認証・RLS・権限の変更／新しい継続アクセス（OAuth・APIキー）／秘密値の登録／デプロイ／既存顧客情報の新サービスへの送信／課金／本番データの補正・取消／請求書の確定発行・送付。

## 8. お金のルール

| 項目 | ルール |
|---|---|
| 単価 | `price_master` のランク別単価が税込表示。顧客指定単価は `price_source` に根拠を書く |
| 送料 | `shipments.freight` は税抜。請求書では10%。箱ごとの内訳は備考 |
| 仲卸 | 注文はお店名義、請求は仲卸あてにまとめる（`wholesalerTagOf`） |
| 書類 | 発行済みは黙って上書きしない。送付済みと見なさない。訂正しても自動再送しない |
| 税・端数・締め | 勝手に変えない |
| 「出荷済」の残り在庫 | 4〜7月の手書きラベル時代の一括「出荷済」2,249件は実物が残っていることがある → 注文に紐づかない出荷済パックは使う前に本人に確認 |

## 10. 実測で分かった弱いところ

| # | 弱いところ | 実測 | 影響 |
|---|---|---|---|
| 1 | 精肉→販売の断絶 | 精肉760頭・販売356頭・在庫1,419パック | 売れ残り・期限切れ |
| 2 | 公開キーの権限が広い | 削除可能な表 149 | 誤操作・悪用でデータが消える |
| 3 | 注文ページがほぼ使われていない | 注文405件中、注文ページ経由はごく一部 | 電話・LINE・手書きの転記が残る |
| 4 | 送料の空欄 | 出荷375件中 57件が送料なし | 請求書の送料欄 |
| 5 | 生態データの欠け | 緯度経度 3件／916 | 捕獲地の解析・物語 |
| 6 | 在庫パックの無い出荷 | 骨・内臓・アライグマ枝肉など口頭指示の明細 | 個体まで辿れない |
| 7 | ラベル番号と在庫番号のずれ | 10/21・11/9 作成分で1つずれ（例 10006310↔10006311） | 出荷時のスキャンで見つからない |
| 8 | 一体保存でない書き込み | 出荷・精肉・加工・請求が別々の書込み | 途中失敗で食い違い |
| 9 | 帳簿の二重管理 | 台帳スプレッドシート・実包管理簿が手作業 | 転記漏れ・記入漏れが起きやすい |

## 12. 運用

| 項目 | 手順 |
|---|---|
| 開発 | `origin/main` から作業ブランチ → PR → 本人の「マージして」で squash merge |
| 反映確認 | 約6分後、DB の `extensions.http_get` で本番HTMLに目印があるか確認（サンドボックスから直接は見られない） |
| マイグレーション | ファイルを PR に置く → 本人の承認 → 適用 → 適用後の権限・関数を照会して確認 |

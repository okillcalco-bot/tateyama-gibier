## C. 提案（実装していない。決めてから進める）

### C-1. 採番体系（ユニークで、市の都合と切り離した番号）【データ】

- **現状**: `TGC-08-T477`（年度＋地区＋地区内連番）。番号を詰める・付け替えると、ラベル・在庫・注文の紐づけを全部たどる必要がある（11/20 の繰り上げで実際に手作業が発生）。
- **提案**: 個体に**変わらない内部番号**を1本追加する（例 `年月 + 自治体コード + 連番` の10桁、または通し番号）。
  - 既存の `label_id`（市に出す番号・ラベルの番号）は**そのまま残す**。内部の紐づけは新しい番号で行う。
  - 追加は「列を足して、既存行に一度だけ採番」で済む。既存の番号・ラベル・バーコードは変えない。
- **決めること**: 番号の形（年月＋自治体コード＋連番でよいか）、市の番号との関係を市に説明するか。

### C-2. 写真の退避【運用】

- **現状**: 写真 約77MB は Supabase の日次バックアップの対象外。
- **提案**: 週1回、Storage の写真を Google ドライブ（2TB 契約済み）へ複製する仕組み（Apps Script または手動の一括ダウンロード）。
- **決めること**: 置き場所のフォルダ、頻度。

### C-3. 秒単位の巻き戻し（PITR）【費用】

- Pro の日次バックアップは「1日1回・7日分・全体を丸ごと戻す」。秒単位の巻き戻しは追加費用（月1.5万円程度〜）。
- **提案**: 今は A の一括保存＋日次バックアップで止血。他施設に提供する段階で再検討。

### C-4. ハードコーディング（`TGC-08` などの決め打ち）【構造】

- **現状**: 画面のコードに `TGC-08`（施設コード＋年度）が **90か所**（index.html 59・capture-form.html 24 ほか）。年度が変わる・他施設で使う、のどちらでも書き換えが必要。
- **提案**: 施設コード・年度・地区記号を**設定（マスタ）**に出し、コードは設定を読む形にする。データは変えない（画面側の変更）。他施設展開の前提になる。
- **決めること**: 年度の切り替え日（4/1）と、年度をまたぐ個体の扱い。

### C-5. ホスティング（Vercel の利用規約）【方針】

- Vercel の **Hobby（無料）プランは非商用限定**。事業で使うなら Pro（月20ドル/人）か、Cloudflare Pages 等への移行が必要。
- **提案**: まずプランを確認（B）。他施設へどう提供するか（各施設に入れるのか、1か所で預かるのか）を決めてからサービスを選ぶ（打合せの結論どおり）。

### C-6. 旧・新システムが同じDBを使うことの管理【構造】

- **提案**: DB の表の定義と、適用済みマイグレーションの一覧を `docs/` に書き出し、表を変える PR では「基幹（静的HTML）」「ALCO OS」の両方の影響を確認する決まりにする。

### C-7. 現場スタッフへのタスク・優先指示【画面】

- **現状**: ダッシュボードに「今日やること」（出荷待ち・通販の集荷・検査前の個体など）がある。
- **提案**: 担当者別・優先度つきの「今日の作業指示」（誰が・何を・いつまで）を追加。管理者が並べ替え、スタッフは終わったら押す。
- **決めること**: 指示を出すのは誰か、スタッフの端末（共有タブレットか各自のスマホか）。

### C-8. 肉質評価の数値化【データ】

- **提案**: 精肉時に **脂の厚み（mm・ノギス）** を入れる欄を個体に追加し、ランク（並・上・極上）の目安を数字で決める（例: 何mm以上で上）。色は写真に**白（グレー）カードを一緒に写す**決まりにして、後でAI判定に使えるようにする。
- **決めること**: 測る場所（どの部位の脂か）、ランクの目安の数字。

### C-9. 環境調査データとの連携【データ・研究】

- **現状**: 捕獲地点の緯度経度は 916頭中3頭だけ。環境調査（山名ハウス等）は Excel＋GPS＋写真。
- **提案**: まず捕獲票で**緯度経度（またはメッシュ番号）**を必ず取る。環境データとはメッシュ（例: 3次メッシュ 約1km）で重ねる。捕獲日に近い季節の調査データと突き合わせる。
- **注意**: 絶滅危惧種（ランなど）の位置は、公開画面では**メッシュより粗くする・出さない**。

### C-10. 他施設への展開・知財【方針】

- 打合せの整理: システムで稼ぐのではなく、施設の作業が楽になること＋全国の獣害データの可視化が目的。
- **システム側で必要になること**: 施設ごとにデータを分ける仕組み（複数施設対応）、C-4 の決め打ちの解消、名前（商標）、導入手順書・操作説明、データ量が一気に増えたときの容量計画。
- **知財**: 仕組みを先に公開して他社の特許取得を防ぐ（防衛的公開）か、独自の予測ロジックだけを非公開にするかを決める。
